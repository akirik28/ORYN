## 2. Method notes (so the numbers above are reproducible)

- All SQL run against project `qtcvcflzxbuagvvwahhu` via `execute_sql`, read-only.
- Link checks: `curl -sS -L --max-redirs 8 --max-time 20 --connect-timeout 8` with a real
  browser UA, 16-way parallel, capturing final HTTP status code after redirects. Anything not
  starting with `2` was treated as "needs a look" and either spot-checked further (headers/body)
  or reported as-is. A 403 was **not** auto-classified as broken — see §6.2 for why.
- Duplicate detection: exact `official_url` GROUP BY; a normalized form (strip `http(s)://`,
  strip leading `www.`, strip trailing `/`, lowercase) GROUP BY; exact normalized-title GROUP BY;
  and `pg_trgm` `similarity()` on lowercased titles for different `id`s (extension is installed —
  `pg_trgm 1.6` in schema `public` — confirmed via `list_extensions`, no fallback needed).
- Image checks: SQL against the EAV table plus direct visual inspection — 22 images downloaded
  with `curl` and viewed directly (not just their metadata) via the Read tool: 20 from the
  `official`/`wikimedia_verified` cohorts (§4.4) plus 2 raw Wikimedia Commons files fetched via
  `Special:FilePath` for rows still in `needs_review`.

## 4. `universities` image infrastructure — correction, then a real quality audit

### 4.1 The correction

The original claim ("`universities.logo_url` is the only image-named column, so real photo
coverage is 0% because there's nowhere to store one") is **only half right**. It is exactly
correct as a literal column-name search. It is **wrong as a coverage conclusion**, because
`universities` has a second, populated, non-crest image store that a column-name search
structurally cannot see: `university_profile_metrics`, an EAV table (`metric_code`/`value_text`
rows, not named columns) written by `scripts/acquire-university-images.ts`.

Confirmed directly:

```
metric_code               | rows with populated value_text
primary_image_url         | 721 (721 distinct university_id)
primary_image_status      | 901
primary_image_license     | ~527
primary_image_attribution | ~510
primary_image_checksum    | 721
```

`primary_image_status` breakdown (901 universities touched, out of 1,019 total — 118 have no
entry at all):

| status | count |
|---|---|
| `wikimedia_verified` | 525 |
| `official` | 194 |
| `needs_review` | 180 |
| `verified` | 2 |

721 distinct universities have a resolved `primary_image_url` (all 721 carry a "good" status —
`wikimedia_verified`/`official`/`verified`; `needs_review` rows carry no resolved URL, by
design). This is **70.8% of all 1,019 universities**, stored at
`university-images/<id>/campus.webp` in Supabase Storage, sourced from Wikimedia Commons (P18
campus photo, distinct from the P154 logo mechanism the same script uses for `logo_url`) or an
official university homepage's `og:image`. This is a real, substantial, deliberately-built
pipeline — not zero, and not a logo/crest by construction (the script explicitly separates the
two mechanisms).

This is why the plain `information_schema.columns` check under-reports: it can only find image
data that lives in a *named column*. Data stored as rows inside a generically-named
`metric_code`/`value_text` EAV table is invisible to that method even though it is real,
populated, queryable data. Worth remembering for any future "does column X exist" sweep on this
schema.

**`docs/design-system.md`'s own text is stale on this point** — it says `opportunities` has no
image pipeline "where universities have both
(`university_profile_metrics.primary_image_url`, `universities.logo_url`,
`scripts/acquire-university-images.ts`)" — so the doc itself already knew about this table; the
only thing that needed correcting was the coordinator's fresh column-search, which repeated the
same blind spot the doc had already worked around.

### 4.2 Why this matters for any "images produced" claim in `data/research/`

Confirmed (§3) that no research-freeze file claims opportunity image coverage. Nothing needed
correcting there. But if any *future* file claims "university images: 0% coverage" or "no image
pipeline exists," that claim would now be directly contradicted by live DB state — 70.8% coverage
is real and pre-dates this freeze week (`verified_at` timestamps cluster around 2026-08-18, over

near-square, not a usable landscape campus photo`, or a download failure. None of the 18 sampled

exists**. Two images fetched directly to confirm this gap concretely:

guarantee should be downgraded pending a full content-based re-audit of all 194 rows;
`wikimedia_verified` status held up well enough in this sample that a blanket downgrade there
would be overcorrecting on current evidence, though it hasn't been checked at full scale either.

## 7. Structural findings (for the coordinator / owning lanes)

1. **`opportunities` has no image storage path at all** — not a data gap, a schema gap. Nothing
   to fix from a QA seat; flagging for whichever lane owns schema/acquisition work.
2. **`universities` image coverage is real (70.8%) but the `official` status label specifically
   overstates quality; `wikimedia_verified` held up well in this sample.** Specifically: (a)
   194/194 `official`-sourced images have no captured usage rights at all — should be
   `RIGHTS_REVIEW_REQUIRED` per the contract's own standard, not silently treated as clear; (b) a
   7-image spot-check of `official` rows found 3 are a flat logo/crest/mascot photo, not a campus
   photo, and a 4th is a real photo of a crest rather than a building (43-57% failure at n=7),
   while a parallel 13-image spot-check of `wikimedia_verified` rows found 0 failures; (c) the
   `needs_review` gate is purely dimensional (resolution/aspect-ratio) with no content-based
   logo/crest/crowd-photo detector, which is both why a logo (`Logoalf.png`) only got caught by
   accident (it happened to also be undersized) and why a good photo (`Kfu.PNG`, King Faisal
   University) sits unpromoted over an 8%-narrow technicality. This matches and independently
   corroborates the cross-lane S9/S3 spot-check result relayed mid-session (Bristol and Stanford
   failing on crest-domination and an unidentifiable crowd photo respectively, Heidelberg
   passing) — my own 20-image sample deliberately used different university IDs than S3's 3, so
   the two samples combine to 23 non-overlapping spot-checks rather than duplicating effort.
3. **5 unresolved opportunity-duplicate clusters remain** (Belin-Blank SSTP, UCSB Research
   Mentorship Program, Lehigh University, Phillips Exeter Academy, Sabancı University Summer
   School) where the same "disable the weaker row" treatment already applied to BU/SAIC/TechGirls/
   Oxford Royale/Rockefeller/Clark Scholars/RSI-at-MIT/Diamond Challenge has not yet been applied.
4. **`opportunities` has no enforced unique constraint on `official_url`**, confirmed by the fact
   that 11 URL-collision clusters exist at all — worth a schema-level conversation (a partial
   unique index, or an application-level dedup-on-insert check) separate from cleaning up the
   current 11 clusters by hand, since 3 of the 11 are legitimate one-URL-many-programs cases that
   a naive unique constraint would incorrectly block.
5. **The Rockefeller SSRP surviving record's `official_url` is currently unreachable** (§6.3) —
   worth a follow-up check outside this automated sandbox (e.g., a real browser load) before
   concluding it's actually down, but it's odd enough (TLS handshake specifically times out,
   twice) to flag rather than ignore.

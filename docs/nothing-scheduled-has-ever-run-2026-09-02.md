# Nothing scheduled has ever run — 2026-09-02

Found while checking oryn-3f's correction to a brief of mine. They were right and the
correction opens onto something larger: several separate "this feature doesn't work"
findings are **one root cause**.

## The measurement

`external_sync_jobs` — the table every scheduled job writes to — contains **exactly one job
name**:

| job | runs | last |
|---|---|---|
| `deadline_reminders` | 2 | **2026-08-22** |
| `discover_opportunities` | **0** | never |
| `discover_requirements` | **0** | never |
| `sync_us_universities` | **0** | never |

All four are declared in `vercel.json` with daily schedules. None has fired. The two
`deadline_reminders` rows are almost certainly the admin panel's own "Run deadline scan"
button, not cron — they share a single day eleven days ago and nothing has happened since.

## The cause

**ORYN has never been deployed.** The Vercel account (`Stem and Buds`, Hobby plan) contains
**zero projects**, and there is no `.vercel/project.json` in the checkout.

`docs/deployment.md` §6.2 states the rule that closes this: *"Cron jobs only run against
production deployments — never previews."* There is no production deployment, so there are
no cron runs. Nothing is misconfigured.

Worth saying explicitly, because it is the natural next worry: **the cron config is already
correct for the plan they're on.** §6.0 documents that Hobby hard-caps every cron at once
per day and rejects a more frequent expression *at deploy time*; all four schedules are
daily and spaced two hours apart deliberately. Cron *count* is not a constraint on any plan.
Deploying does not require moving to Pro.

## What sits behind this one gate

These have each been reported separately, at different times, as their own gap:

- **`deadline` notifications have never fired.** The code path existed; the job that calls
  it hasn't run in eleven days.
- **Opportunity discovery has never run**, so the catalogue only holds what was ingested by
  hand.
- **University sync and requirement discovery have never run**, which is part of why
  freshness metadata across the catalogue is as old as it is.
- **Every weekly plan in the database was generated by a student sitting on the page**, not
  on a schedule — previously attributed to Job D not existing, which was true, and now also
  true of the four jobs that *do* exist.

None of these is a code defect. They are all downstream of one unfinished setup step.

## What this changes

"Production setup" has been sitting on the founder's blocked backlog as a single line
alongside a domain and SMTP. It is not one item among several — **it is the gate four
subsystems sit behind**, and none of them can be tested, measured, or trusted until it is
done. The first production deploy converts four never-observed jobs into four jobs with
actual run histories, which is also the first moment the admin panel's job-health section
becomes meaningful rather than uniformly red.

`CRON_SECRET` is worth flagging in the same breath, since it is the one variable that
behaves differently: Vercel attaches it as a bearer token to every cron invocation and
`verifyCronRequest` is **fail-closed** — unset means every cron request is rejected,
including Vercel's own. Deploying without it produces exactly the symptom above, and would
be indistinguishable from it.

## Deploy readiness, checked rather than assumed — same night

Since "deploy it" is now the top item, I checked whether it would actually work.

**The production build passes.** `npm run build`, exit 0, every route compiled. Nothing in
the app blocks a deploy.

**Integrations, from `npm run check:integrations` — real calls, no secrets printed:**

| | |
|---|---|
| Supabase (publishable + secret) | **OK** |
| Anthropic | **OK** |
| OpenAlex | **OK** |
| **Tavily** | **missing credential** |
| **College Scorecard** | **missing credential** |

Both are present in `.env.local` as **empty values** — declared, never filled.

**This matters more than it looks, because of which jobs they feed.** Deploy today and all
four crons start firing, but two of them can do nothing:

- `discover_opportunities` needs **Tavily**. Without it, opportunity discovery runs and
  finds nothing — the single job most responsible for the catalogue growing on its own.
- `sync_us_universities` needs **College Scorecard**. Without it, US institution data never
  refreshes.

The repo already anticipates exactly this failure and it is worth reading in the admin
panel's own words: several jobs "degrade to a no-op `success` when a provider credential is
missing", which is why the empty-streak detector exists to tell *"found nothing new
tonight"* apart from *"hasn't accomplished anything in a week"*. Without these two keys, the
job-health section would show two jobs succeeding nightly and processing zero items — green
badges, no work — and the empty-streak warning is the only thing that would say so.

**So the deploy checklist has three parts, not one:**
1. Create the Vercel project and deploy to production.
2. Set `CRON_SECRET` — fail-closed, so without it every cron request is rejected including
   Vercel's own, producing a symptom indistinguishable from not having deployed at all.
3. Fill `TAVILY_API_KEY` and `COLLEGE_SCORECARD_API_KEY`, or accept that two of the four
   jobs will run green and do nothing, and know which two.

`SENTRY_DSN` is in `.env.example` and absent locally. Not a blocker; noted so the absence is
a decision rather than an oversight.

## Worktree hygiene — the integrator removes it, at merge time

**Standing rule, adopted 2026-09-01.** When a branch merges to `main`, whoever performed
the merge removes its worktree as part of that same step — not on a later sweep.

The reason it is written down: a periodic cleanup pass does not hold. This machine went
6.8Gi → 12Gi → 6.8Gi → 12Gi across a single night of parallel lanes, and it was caught each
time by someone noticing rather than by the process. Overnight working sessions deliberately
skip end-of-session cleanup, so worktrees accumulate between passes with nothing to stop
them. Attaching removal to the merge makes it happen exactly as often as it needs to.

### Do it in the same command as the merge, not after it

**Written down twice and still not followed.** After the sweep incident above, four
consecutive branches were merged over about two hours and not one of their worktrees was
removed — they accumulated 5.7Gi between them and were found only because someone was
watching free space, not because the rule fired. The failure is not the rule's content; it is
that "remove it afterwards" is a second action, and second actions get dropped when the next
lane's report is already waiting.

So: `git merge … && git worktree remove …` in one command, or it will not happen. If the
worktree is not clean at that moment, the branch was not ready to merge.

### Remove the one branch you merged, by name — never sweep

**The rule is per-merge, not periodic, and that distinction has teeth.** On 2026-09-01 the
integrator ran a sweep over "everything that looks merged" and deleted
`oryn/i18n-advisor-2026-09-01`'s worktree three minutes after a lane created it. Both safety
checks passed and both were meaningless there: a freshly-cut branch is an ancestor of `main`
from the instant it exists, and a worktree nobody has written to yet is clean. Nothing was
lost — there was nothing in it — but the sweep is what made that possible, and no check can
rescue a sweep from removing something that does not exist yet.

So: after merging branch X, remove branch X's worktree. Do not enumerate.

### Before removing anything: "merged" is not "idle"

**A branch freshly cut from `main` is an ancestor of `main` from the instant it is created**
— before a single commit lands on it. So "fully merged" and "safe to remove" look like the
same question and are not, and the gap is widest exactly when a lane has just started work.
This nearly cost a lane its setup on 2026-09-01: `oryn/i18n-dashboard-2026-09-01` appeared
in a merged-branch listing about ninety seconds after the lane claimed it.

Confirm the lane is finished with the worktree. Do not infer it from the graph.

The second check:
- **Check for uncommitted work** (`git -C <worktree> status --porcelain`) before
  `git worktree remove --force`. `next-env.d.ts` is regenerated by `next dev` and can be
  ignored; anything else means stop and ask the lane.

Lanes are welcome to remove their own worktree after pushing — several already do, and that
is strictly better. This rule is the backstop for the ones that don't.

If you're about to create `ORYN_MASTER_PLAN.md`, `ORYN_STATUS.md`, or `ORYN_DECISIONS.md`,
stop — those roles are already filled by the files above. Only this ownership table was
genuinely missing as of 2026-08-20.

## How to use this file

Before starting a substantial new package: `git fetch --all --prune`, re-read this file,
confirm nobody already owns what you're about to do. Claim your row (update it) before
starting large work; update it again when you finish or hand off. Do not rewrite another
agent's row from assumption — verify from git log/live DB first, then correct with
evidence if it's actually wrong.

## Two lessons from tonight (2026-09-02), folded into the rules above

**One writer per directory.** A research session branched inside the canonical checkout
(`/Users/adasarpkirik/Desktop/Founder/ORYN` itself, not a dedicated worktree) while the
integrator had uncommitted work sitting in that same directory — the uncommitted work landed
on the research session's branch, not the integrator's. The canonical checkout is for
reading, merging, and worktree management; nobody does feature work in it. Every task —
including a one-file doc edit like this one — gets its own `git worktree add`, no exceptions
for "it's small."

**Branch names identify a worktree's owner — directory names do not, and stop trusting
them once a worktree is reused.** `ORYN-wt-tr-depth` has hosted three unrelated assignments
tonight; as of this writing it holds `oryn/schema-type-drift-audit-2026-09-02`, nothing about
Turkey. `git worktree list` prints the branch each path is actually on — read that column,
not the path. If you're about to write "the X lane" based on a directory name, `cd` in and
check `git branch --show-current` first.

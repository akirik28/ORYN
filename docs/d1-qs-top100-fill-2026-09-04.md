# D1 — QS top-100 fill, 2026-09-04

CEO (oryn-5b) assignment, PROXOLA-PLAN.md D1: 695 of 1010 universities (68.8%) show no
content. Follow-on to the 9-university fill (2026-09-03, `docs/fill-9-universities-findings-2026-09-04.md`) —
that batch was top-50 QS, US/UK/Europe-heavy. This batch, confirmed with CEO after correcting
a scope misattribution (see the session's own report), targets the genuinely empty top-100-caliber
institutions found by live query, concentrated in Asia-Pacific + Toronto: **NUS, Tsinghua,
Peking, KAIST, Kyoto, Seoul National, Melbourne, Sydney, Tokyo, Monash, HKUST, Hong Kong
Polytechnic, University of Hong Kong** (fully empty — zero requirements/statistics/sources)
plus **Toronto, NTU Singapore, CUHK, City University of Hong Kong, UBC, Copenhagen**
(near-empty — one source, zero requirements/statistics).

Rules applied throughout, per the plan's own D1 item: official source only (university page →
government dataset → application platform; secondary source last resort, labeled), every fact
gets `source_url` + retrieval date, a field with no official answer found is left NULL rather
than estimated, `admission_rate_basis` set correctly when an admission rate is written
(`'published'` only when a real rate is found; a not-found rate stays the table's own
`'not_researched'` default, never guessed as `'no_single_rate'` — that label is reserved for a
confirmed multi-valued admission structure, per the 9-university batch's own precedent).

**A separate, real data-quality issue found while scoping, not part of this fill:** apparent
duplicate rows — MIT appears twice, HKUST appears twice (`75761b06-...` and `29e16fe0-...`,
the second with null `website_url`/`admissions_url`/`student_size`), and "UCL" /
"University College London" look like the same institution split across two rows (one has 16
requirements, the other zero). Filling the empty duplicate would be wasted effort or, worse,
create conflicting data for the same real institution once merged. Not touched here — flagged
to CEO, de-duplication is a separate task.

**SQL below is staged, not applied** — per standing rule 2, CEO/founder runs it.

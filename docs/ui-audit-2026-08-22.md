- **Account**: QA persona `oryn.qa.a@example.com` (admin), essentially empty profile

  an accurate stand-in for AGENTS.md's Persona D ("early-stage 14-year-old with little
  profile history"), so most of this audit is really an empty/low-data-state audit.
- **Checked against**: AGENTS.md Phases 43–47 (empty/loading/error states,
  accessibility, responsive), `docs/design-system.md` conformance, and
  `docs/empty-loading-error-state-audit.md` (re-verified rather than trusted — it's
  accurate as far as it goes; see §4 for what it didn't cover).
- **Breakpoints**: mobile (375×812), desktop (1280×800). Tablet not separately walked —
  the app's only real breakpoint-sensitive logic (`useIsDesktop`, `md`/768px) was
  confirmed in source and behaves correctly at both tested widths, so a 768px pass
  would mostly re-confirm the same code path rather than find something new.
- **Tool caveat, stated plainly so it isn't mistaken for a product defect**: the
  Browser-pane screenshot tool intermittently painted blank on this session (after a
  JS-driven scroll, immediately post-navigation before a dynamic import settled, and

## 2. Defects — safe to fix now

Ranked by user impact. Each is single-file or two-file, theme-independent, no shared-

ORYN-CEO's scoping.

### 2.1 "Generate my plan" fails silently when AI isn't configured — **HIGH** — ✅ shipped, PR #34

Verifying this fix live surfaced that §3.1 below was itself wrong — see that section's
own correction, not repeated here.

- **Route**: `/plan` (and the dashboard's own auto-generate path — same error, same fix
  family)
- **File**: [features/dashboard/generate-plan-button.tsx](features/dashboard/generate-plan-button.tsx)
- **Repro**: with `ANTHROPIC_API_KEY` unset (true in this dev environment), click
  "Generate my plan." Network tab shows `POST /plan → 200 OK`. Console shows
  `AIProviderNotConfiguredError: ANTHROPIC_API_KEY is not set`. The page shows **nothing**
  — no toast, no inline message, button just returns to idle.
- **Root cause, precisely**: the server action already does the right thing —
  [app/(app)/plan/actions.ts](<app/(app)/plan/actions.ts>)'s `regenerateWeeklyPlan()`
  catches `AIProviderNotConfiguredError` specifically and returns
  `{ error: "The AI Advisor isn't configured yet, so weekly plans can't be generated.
  See API_SETUP.md." }` — a correct, human-readable, Phase-72-compliant message. The
  bug is entirely client-side: `generate-plan-button.tsx` does
  `if (!result.error) router.refresh();` and has no `else` — the message is computed
  and then discarded.
- **Why it matters**: Plan is the direct UI for Phase 9 (Weekly AI Review), one of the
  product's core loops. A student who clicks this and sees nothing will conclude the
  button is broken, not that a server credential is missing — indistinguishable from
  the exact anti-pattern AGENTS.md Phase 44 names ("do not show frozen buttons").
- **Fix shape**: add the `else` branch, surface `result.error` via the `sonner` toast
  pattern already used elsewhere in the app (e.g. `OpportunityActions`'s rollback
  toast) for mutation failures. ~2 lines, one file, matches an existing convention
  exactly — not inventing a new UI pattern.

### 2.2 Two text instances fail WCAG AA contrast — **MEDIUM-HIGH** — ✅ shipped, PR #72

Fixed within the existing palette only, per explicit instruction: dropped the `/70`
opacity modifier back to the plain, already-passing token — no new color, no `dark:`
variant touched, no theme decision made.

- **Routes**: `/universities` (list — every university card), `/universities` (list —
  "N countries aren't yet mapped to a region" note, shown when applicable)
- **Files**:
  [features/universities/university-card.tsx:128](features/universities/university-card.tsx#L128),
  [app/(app)/universities/page.tsx:428](<app/(app)/universities/page.tsx#L428>)
- **Measured, not eyeballed**: both use `text-muted-foreground/70` — the *already-passing*
  `text-muted-foreground` (5.09:1 against a white backdrop, confirmed by compositing the
  computed color onto a canvas pre-filled white and reading back the resulting opaque
  RGB — not just reading the declared color, which for an alpha color returns the
  un-composited value and understates how light it actually renders) with a 70% opacity
  modifier stacked on top, which composites down to **2.82:1** (same method, on the
  `university-card.tsx` instance — an 11px uppercase "Research focus" kicker). Both fail
  WCAG AA for normal-size text (needs 4.5:1); the `/128` instance is 11px, nowhere near
  the "large text" 3:1 exception either. Checked whether a lighter-than-full-opacity
  compromise exists: `/80` on the same base color composites to only **3.40:1** —
  clears the large-text 3:1 bar but still fails AA's normal-text 4.5:1, so it is not a
  usable alternative here, not for text this size.
- **Why it matters**: this repeats on every university card that has a research-focus
  line — the highest-traffic list page in University Explorer.
- **Fix shape**: drop the `/70` opacity modifier on both (→ plain `text-muted-foreground`,
  verified 5.09:1). One class edit per file — the only verified-passing option at this
  font size, not a choice between equally-valid alternatives.

### 2.3 Two search inputs have no accessible name — **MEDIUM** — ✅ shipped, PR #69

- **Routes**: `/search` (the dedicated global search page), `/universities` (the
  in-page "Search by university name…" combobox)
- **Files**: [app/(app)/search/page.tsx:27](<app/(app)/search/page.tsx#L27>),
  [features/universities/university-search-box.tsx:97](features/universities/university-search-box.tsx#L97)
- **Detail**: both rely on `placeholder` alone — no `<Label>`, no `aria-label`. Placeholder
  text is not a reliable accessible name (it disappears once text is entered, and
  isn't consistently exposed by every screen reader). The university one is worse:
  it's `role="combobox"` with `aria-expanded`/`aria-controls`, which makes it an ARIA
  widget that specifically needs a computed accessible name to announce correctly.
  For contrast, the same combobox pattern is done correctly everywhere else in the app
  — the ⌘K `CommandPalette` has `aria-label="Search"` on its input, and every
  `SuggestInput` call site (`onboarding-wizard.tsx`, `location-form.tsx`,
  `citizenship-form.tsx`) pairs it with a real `<Label htmlFor>`. These two are the
  only two gaps in an otherwise-consistent pattern.
- **Fix shape**: `aria-label="Search Oryn"` / `aria-label="Search universities"`. One
  line each.

### 2.4 Advisor chat's send button has no accessible name — **LOW-MEDIUM** — ✅ shipped, PR #69 (same PR as §2.3, same defect class)

- **Route**: `/advisor` (once profile completeness unlocks the chat)
- **File**: [features/advisor/advisor-chat.tsx:201](features/advisor/advisor-chat.tsx#L201)
- **Detail**: `<Button type="submit" size="icon" ...><ArrowUp className="size-4" /></Button>`
  — icon-only, no `aria-label`. The other three icon-only buttons in the app
  (`notification-bell.tsx`, `mobile-nav.tsx`, `conversation-thread.tsx`'s message-send
  button) all have one; this is the one gap.
- **Fix shape**: `aria-label="Send message"`. One line.

### 2.5 Profile page stacks four `rounded-3xl` "hero" sections — **LOW (consistency)**

- **Route**: `/profile`
- **File**: [app/\(app\)/profile/page.tsx](<app/(app)/profile/page.tsx>) lines 211, 227,
  232, 257
- **Detail**: `docs/design-system.md` states its own rule directly: *"There should be at
  most one `rounded-3xl` element per screen — it's a 'this is the point of this page'
  signal, not a size utility."* This page has four, stacked vertically (`Professional
  profile`, `Featured`, `Profile Strength`, the dimension-scores panel) — confirmed via
  DOM query, not a guess. Visually this dilutes the "hero" signal the design system is
  trying to create; every section reads as equally important, which is the opposite of
  the intent.
- **This is a real rule violation, not a taste call** — the app's own documented
  standard is being broken. *How* to resolve it (which section stays `rounded-3xl`, or
  whether the rule itself should flex for a page with several genuinely-important
  sections) is a judgment call — see §5.A rather than deciding it here.

## 3. Findings for other lanes (not UI-1's to fix)

### 3.1 ~~Dashboard "Due soon" shows four indistinguishable entries~~ — RESOLVED, and this section's own original diagnosis was wrong

**Correction, not a live finding.** This section originally called the four identical
"Yale University — scholarship" dashboard cards a data question — four
`university_deadlines` rows genuinely sharing `deadline_type='scholarship'` — and routed
it to research org rather than fixing it, on the stated reasoning that
[lib/deadlines/upcoming.ts:124](lib/deadlines/upcoming.ts#L124) "already includes a
differentiator field; it's rendering correctly." That premise was never actually
verified against the full row shape — only assumed from the one field the title string
uses. It was wrong: ORYN-BASORG confirmed live that the four rows are genuinely distinct
cycles (Early Action US/PR citizens, Early Action international citizens, Regular
Decision, Transfer), and the real distinguishing data — `cycle_label` and
`deadline_text_verbatim` — existed on the rows all along; neither field was ever
selected or rendered by the "Due soon" query or the deadline-reminder notification path
that mirrors it. It *was* a UI bug, not a data question. Fixed in
[PR #42](https://github.com/akirik28/ORYN/pull/42) (merged): a `deadlineDetailLabel()`
helper prefers `deadline_text_verbatim`, falls back to `cycle_label`, falls back to
`deadline_type` only for older rows with neither — applied at both call sites. Verified
live on QA account A's real seeded Yale rows: the four cards now read the actual cycle
names/dates instead of one repeated string.

Left in this document, corrected rather than deleted, for the same reason the rest of
this audit insists on citing evidence: a wrong finding that quietly disappears is worse
than one that's visibly struck through and explained — the failure mode here was
treating "the code reads *a* field" as proof of "the code reads *the right* field,"
without checking what fields the row actually carried. Worth remembering on the next
"this must be a data problem" call.

## 5. Point of view — proposals for this evening's conversation

**These are proposals to react to, not decisions already made.** Each is grounded in
either a concrete defect above or a specific line from AGENTS.md's own stated design
philosophy — not a general "I don't like it." Each is tiered by cost/risk so you can
pick with real information:

> **Tier key** — 🟢 color/typography/spacing: cheap, contained, reversible, safe to
> iterate live. 🟡 density/hierarchy: touches layout, not data flow, medium effort.
> 🔴 information architecture: which screens exist / what's on which page — wide blast
> radius, constrained by AGENTS.md Phases 42/53, not a same-evening call.

None of these is 🔴. Theme (light/dark, accent hue) is deliberately not included —
`founder-blocked-backlog.md` item 11 stays open; nothing here infers a preference.

### A. Profile page: pick one hero, not four 🟢

The rule violation is §2.5 — four stacked `rounded-3xl` sections. The fix is cheap;
the actual decision is *which section is "the point of this page."* Three real options:

1. **Keep only the dimension-scores panel** (`Academics / Curiosity / Leadership /
   Research / ...`) as `rounded-3xl`, demote the other three to `rounded-xl`/`rounded-2xl`
   per the doc's own tier table. Argument: this panel *is* the Career Profile in
   miniature — the thing the whole page exists to show.
2. **Keep the top "Professional profile" section instead** (it's what the student sees
   first, and it's the one other students would see on a public profile). Demote the
   rest.
3. **Change the rule, not the page.** If the repeated `rounded-3xl` rhythm actually
   reads as "this is one continuous, important surface" rather than "four competing
   heroes" to you, that's a legitimate different read of the same page — in which case
   the fix is a one-line edit to `design-system.md`'s rule, not four class changes.

My read: option 1, because it's the one place on the page a returning student should
look first ("did my profile improve"), and AGENTS.md's own dashboard mockup treats the
score as *the* headline element everywhere else in the product. But this is a real
preference call — any of the three is defensible.

### B. ~~"Due soon" cards need to be tellable apart~~ — resolved by the §3.1 fix, nothing left to propose

This originally proposed two workarounds (append the date into the label; group
same-university deadlines into an expandable card) for what looked like a permanent
data-shape limitation. It wasn't one — §3.1's fix renders the actual distinguishing
field, so the cards are already tellable apart by what they *are* ("Early Action
international," "Regular Decision"), which is strictly more useful than either
workaround here would have been. No open proposal left in this slot. The one part of
the original idea that might still be worth a look later — whether four real, correctly-
labeled deadlines for one school ever crowd the "Due soon" list uncomfortably — is
speculative with no evidence behind it now that the labels are meaningful, so it isn't
carried forward as a proposal; flag it only if it's actually observed to be a problem.

### C. ~~The silent-failure pattern in §2.1 may not be a one-off~~ — checked by FEAT-2, mostly closed, one item left and it's a real cross-lane call

This originally asked whether option (b) — a scoped audit for the same pattern elsewhere
— was worth doing. It was: FEAT-2 ran exactly that audit independently
(`docs/feat2-error-surfacing-audit-2026-08-22.md`), found 3 more instances, and has
already fixed 2:

1. **`weekly-focus.tsx`'s `updateActionStatus`** (worst of the three — an optimistic UI
   update with no rollback, so a failed save left a checkbox showing "completed" forever,
   an active false-success claim rather than a merely-silent one) — **fixed**.
2. **`notification-bell.tsx`'s two mark-read actions** (smallest — self-correcting on
   next load, but still silent) — **fixed**.
3. **`achievement-section.tsx`'s `handleDelete`** — the widest blast radius of the three
   (backs delete for every achievement type sharing the generic form: Activities,
   Projects, Awards, Research, Volunteering, Work, Education, Test Scores,
   Certifications, Sports, Goals) — **still open, deliberately**. FEAT-2 flagged it
   correctly rather than fixing it alone: the component has one `onDelete` prop, not ten,
   so a fix here isn't scopable to just one lane's territory — most of those achievement
   types belong to profile/FEAT-1's domain, not FEAT-2's. This is a real
   "whoever owns `features/profile/` should pick this up in coordination" item, not a
   proposal with options — noted here only so it's visible in one place rather than
   two lanes' separate docs.

## Why 100% accepted, uniformly, is the correct result here — not the Glasgow pattern

A batch returning 100% accepted / 0% duplicate at every institution is exactly the shape that
hid a real defect in the Glasgow batch (I1-2), so this was checked rather than reported as a
clean pass on its face:

- **Confirmed before the dry-run ran**: live Australia has 0 programme rows across all 37
  universities, UNSW/Sydney/Monash included — not inferred from the dry-run's own output.
  Since the count is 0 in aggregate and per-university counts can't be negative, every one of
  the three target universities individually has 0 pre-existing rows. There is nothing live
  for any of these 544 records to duplicate against — a 100% accepted rate isn't merely
  plausible here, it's the only mathematically possible truthful outcome given a genuinely
  empty baseline.
- **Checked for the failure mode that actually broke Glasgow — within-batch collisions —
  separately from the live-duplicate question**: the analysis wrapper processes records
  sequentially and adds each accepted decision's dedup key to the candidate pool before the
  next record is checked, so two records in this same batch with identical
  `university|name|degreeLevel|language|URL|degreeType` would show the second as `duplicate`,
  not `accepted`. Zero such collisions occurred across all 544. Also checked
  `research_program_id` uniqueness within the batch directly (separate from the dedup-key
  check): 544 loaded, 544 unique — no internal ID collisions either.
- **Glasgow's problem was a live row existing under a different naming/degree_type
  convention than the file describing it** — a mismatch the dedup key couldn't see because
  both sides existed but disagreed. That specific failure mode requires a live row to
  disagree with in the first place. It cannot occur against an empty table, and Australia's
  table is confirmed empty for these three universities.

So: uniform 100%-accepted here reflects a genuinely empty baseline plus a genuinely clean,
non-colliding research batch, not a proxy failing to detect a real duplicate. Reported the
reasoning, not just the number, per the standing instruction that a suspiciously clean result
gets looked at harder rather than proceeded on faster.

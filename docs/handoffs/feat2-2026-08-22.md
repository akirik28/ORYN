## One thing worth carrying forward as a working pattern, not just a finding

P8's actual product insight, per CEO's framing: **when two facts genuinely need to
coexist, the fix is two rows, not one field fighting over both values.**
`university_deadlines.verification_state` already does this correctly (one row per dated
event, so "last cycle closed" and "next cycle not yet published" can be two separate rows
instead of one contested enum) — a working precedent already shipped in this codebase,
not a new design proposal. Worth reaching for before inventing a new enum value the next
time a "one field, several simultaneous truths" problem shows up anywhere in the app.

## Addendum, same day: a `cp -Rc` node_modules scare, resolved

After this document's first version, CEO reported hitting 22 unrelated
`entity-combobox.test.tsx` failures on a branch whose only change was one new script
file, with the theory that `cp -Rc`-cloning `node_modules` from the primary checkout
(`oryn/hide-social-nav`, 212 commits behind `main`) carries forward a mismatched
dependency tree. Every worktree in this session was set up exactly that way — cloned
from the primary checkout — so this was worth taking seriously rather than assuming it
didn't apply here.

Checked two things, not one:

1. **Diffed `package.json`/`package-lock.json` between the primary checkout and
   `origin/main` directly.** `package.json` differs cosmetically (two `scripts` entries);
   `package-lock.json` — the file that actually governs `node_modules` content — is
   **byte-identical**. The 212-commit gap hadn't touched dependencies.
2. **Didn't stop at that inference.** Deleted the cloned `node_modules` in the #47
   worktree (the highest-stakes behavioral PR in this session, and the same category of
   test — an RTL/jsdom component test — as CEO's failure), ran a genuine `npm ci` from
   scratch (765 packages, 0 vulnerabilities), and re-ran the full gate: lint clean,
   typecheck clean, **125 files / 1,895 tests passing, build succeeds — exactly matching
   the number already reported for that PR.** No drift, no phantom failures.

**Deliberately did not re-run the other seven branches.** Same setup pattern, same
identical lockfile, and #47 was the single highest-stakes case (real production
behavior change, real optimistic-state rollback, the newest RTL-test category in this
territory) to check as a representative sample — a chosen scope, not an oversight left
implicit.

CEO subsequently retracted the *cause* (the lockfile evidence above disproved the
"212-commits-behind → mismatched packages" theory) while confirming the *practice*: the
22 failures were real, their actual mechanism is still unknown (candidates: a
partially-completed clone, or contaminated-tree residue from branch reuse — rule 18
territory), and "clean `npm ci` before reporting a number" remains correct regardless of
which explanation turns out to be right. Recording the full sequence here rather than
just the conclusion, since the retraction is itself useful org history: a plausible,
specific-sounding cause was wrong, and the way it got caught was direct verification, not
a more convincing theory.

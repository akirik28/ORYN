## 1. Does an aggregated notification render legibly, or become a wall of text?

**Neither, as shipped — it silently stopped clamping at all.** `notification-bell.tsx`'s body
span was `className="mt-0.5 line-clamp-2 block text-xs leading-[1.45]"`. The literal `block`
utility computes `display: block`, which overrides `line-clamp-2`'s own required
`display: -webkit-box` — Tailwind's line-clamp utility is inert without that display mode. Both
classes were present; `block` won.

Verified empirically in the running preview, not just read from source: with `block` in place,
a 4-item deadline digest (199 chars) rendered all ~5 lines in full (`scrollHeight === clientHeight
=== 87px`) instead of clamping to 2. Removing `block` (tested live before touching source)
restored real clamping: `clientHeight: 35px` (exactly 2 lines), `scrollHeight: 87px` hidden
beneath. Both `lib/deadlines/scan.ts` and `lib/scoring/profile-update-notification.ts` have
comments explicitly describing this component as "a plain `line-clamp-2` span" — the writers on
both sides believed the clamp was working; it wasn't.

**Fixed**: removed the stray `block` class
(`features/app-shell/notification-bell.tsx`). One line. No test added — this is a CSS
correctness fix with direct empirical before/after verification in a real browser (jsdom
doesn't compute layout, so a unit test can't assert clamping); adding one would just assert the
className string, which is the failure mode that let this regress unnoticed in the first place.

## 2. Is there a way to mark things read, or do 20 unread become 200?

**Marking read works correctly — both per-item (click any row) and in bulk (`markAllNotificationsRead`,
which updates every unread row for the user with no `.limit()`, not just what's visible). The
bug is upstream of that: the unread badge undercounts.**

`app/(app)/layout.tsx` fetches only the 20 most recent notifications
(`.order("created_at", {ascending: false}).limit(20)`), and `notification-bell.tsx` derived
`unreadCount` from that same capped array (`notifications.filter(n => !n.read_at).length`). For
any account with ≤20 unread this is exactly right. For the one live account with 103 unread, the
badge could show at most 20 — and given this account's 20 most-recent rows are virtually all
unread (it's a spam backlog, rarely opened), it would show **exactly 20**, matching "the
founder's own account shows 20 unread" almost too precisely to be a different cause.

**Fixed**: added a dedicated exact-count query
(`.select("id", {count: "exact", head: true}).is("read_at", null)`, the same pattern already
used in `lib/counselor/state.ts`, `lib/ai/rate-limit.ts`, `lib/scoring/monthly-review.ts`) run
alongside the existing fetch in `app/(app)/layout.tsx`, threaded as an explicit `unreadCount`
prop through `Topbar` → `NotificationBell` and `MobileNav` → `NotificationBell`, replacing the
derived filter. Made the prop required (not an optional fallback) specifically so no future
caller can silently reintroduce the same bug by omitting it. Added a regression test
(`__tests__/app-shell/notification-bell.test.tsx`) that renders with a `notifications` array of
one item but `unreadCount={103}` and asserts the badge shows "103 unread" — pins the fact that
the badge reads the prop, not the list length.

**Still true after this fix, and not addressed — see §5**: the popover itself only ever shows
the 20 most recent notifications. The badge will now correctly say "103 unread"; the list below
it still shows 20. There is no way to individually see or act on notifications 21–103 — only
"mark all read" reaches them, and it does so without the student ever having read what they
said.

## 3. Does it group, or is it a flat reverse-chronological list?

**Confirmed flat.** `notifications.map(...)` in render order, sourced from a single
`.order("created_at", {ascending: false})` query — no grouping by category, by date, or
otherwise. Not treating this as broken on its own: a flat list of ≤20 items (post-fix, the
visible list is still ≤20) is a normal, legible pattern and plenty of real notification centers
use exactly this. Noting it because it was one of the five things asked about, not because it
needs a fix.

## 4. Does each notification go somewhere useful? (the link-dedup risk)

**Confirmed not a live risk.** The concern named in the brief — old plan notifications sharing
one generic link, and two different things suppressing each other under link-based dedup — does
not apply to the categories that actually dedup against history:

- `deadline_notification_log` (migration `0075`) keys on
  `(user_id, source, source_id, threshold_days)` — explicitly not `link`, per the migration's
  own comment written for exactly this reason.
- `weekly_plan`'s per-ISO-week check (`lib/plan/persist.ts`) keys on `(user_id, category,
  week_start_date)`.
- `new_opportunity`'s dedup (per `docs/handoffs/notification-categories-audit-2026-09-01.md`)
  keys on `(user_id, opportunity_id)`, once ever.
- `profile_update` has no dedup-against-history at all — it's gated at generation time
  (`NOTIFIABLE_DIMENSION_DELTA`, completeness milestones) rather than deduped against prior
  notifications, so there's no link involved in suppressing it either.

And every category's link is distinct and specific: `/dashboard` (deadline digest),
`/profile/history` (profile update), `/opportunities` (new opportunity), `/plan` (weekly plan).
No shared generic link exists among the categories that actually fire today or are about to.
Nothing to fix here.

## 5. Mobile

Checked the actual mobile position, not just the responsive class. The bell lives in a sticky
top header (`features/app-shell/mobile-nav.tsx`), not the bottom tab bar — a normal,
thumb-reachable placement. At a 375px viewport, the `w-80` popover (anchored `align="end"`)
renders at `left: 19.85px, right: 323.85px` — comfortably inside the viewport on both sides, no
clipping. The clamp fix in §1 applies identically here since it's the same shared component.
This one isn't where it hid.

2. **Unread badge derived from a capped 20-row list instead of a real count** —
   `app/(app)/layout.tsx` (new count query), `features/app-shell/topbar.tsx`,
   `features/app-shell/mobile-nav.tsx`, `features/app-shell/notification-bell.tsx` (prop

## What's a product decision, not decided here

**The popover shows at most 20 notifications, ever, and there is no other view.** Post-fix, the
badge is honest about the true total; the list underneath still hard-caps at 20 with no
pagination, no "load more," and no dedicated `/notifications` page to route to (the
`app/(app)/notifications/` directory contains only `actions.ts` — no `page.tsx`). For the one
live account with 103 unread, the only way to clear the backlog is the all-or-nothing "mark all
read" — there is no way to see, individually triage, or link into notification #47.

This is a real gap, but the fix isn't a one-line correction the way the two above were — it's a
scope decision: raise the popover's cap (doesn't scale — 103 already exceeds a raised-to-30 or
even -50 cap, and will keep growing for an actively-notified account), add pagination/infinite
scroll inside the popover, or build a dedicated notifications page (Phase 24 calls for an
"in-app notification center" as V1 scope, which arguably implies more than a topbar dropdown)
with the popover staying as a capped preview and a "View all" link. Each has real layout and
interaction-model implications for a component this session didn't design from scratch — flagging
rather than picking one.

# Part 2 — the notifications page

oryn-a7's call on the fork: build the full page, not raise-and-paginate the popover. Reasoning
(theirs): #21 was unreachable by anything but all-or-nothing "mark all read", which destroys
information to navigate — same shape as the applications dead end from earlier tonight — and
the cap was about to get hit in normal use once `deadline`/`profile_update` start producing
real volume, not just at the tail.

## 1. What's new

**`app/(app)/notifications/page.tsx`** — server-rendered, `searchParams`-driven
(`?category=&page=`), matching this codebase's established convention
(`app/(app)/opportunities/page.tsx`). 25/page (deliberately larger than the popover's 20, so
the page reads as "more," not "+5"), offset pagination via `.range()`, category filter via
`.eq("category", ...)`. Three parallel queries: the current page's rows, a total count for
that filter (pagination math), and a *global* unread count (`Mark all read` always clears
everything regardless of which filter is on screen, matching what the action itself already
does — the button's gating has to match its real effect).

**`features/notifications/notification-list.tsx`** (client) — the page's row list. Full body
text, no `line-clamp` (the page has room; the popover doesn't, see part 1 §1). Each unread row
gets an explicit, properly-labeled "Mark read" button — not just the popover's tiny decorative
dot repurposed as a click target, which would fail a reasonable touch-target-size bar. Clicking
a row's title still marks it read too (same behavior as the popover), so the two paths are
consistent, not competing.

**`features/notifications/mark-read.ts`** — `markReadIfUnread` / `markAllRead`, the actual
"skip if read, call the action, toast on error" logic, extracted so the popover and the new
list call the literal same function rather than two copies that could quietly drift — which is
exactly the kind of divergence part 1 was watching for elsewhere (the `line-clamp-2` fix and
the `unreadCount` fix were each a case of two things that were supposed to agree silently not
agreeing).

**`components/oryn/pagination.tsx`** — had zero callers anywhere in the codebase before this
(confirmed by grep) and hardcoded English `"Previous"`/`"Next"`/`"Page X of Y"` with no
translation. Made the four labels required props while giving it its first real caller, so
this page's "both locales" requirement can't silently regress for whoever calls it next — same
"required, not optional-with-a-silent-default" shape as `unreadCount` in part 1.

**Category filter**: 7 of `NotificationCategory`'s 8 values (`system` excluded — no writer,
ever, per the earlier audit). `university_data_changed` **went live mid-task** — commit
`afa33a57` landed on `main` while this was being built, giving that category its first real
writer (`lib/universities/data-change-scan.ts`). Checked it against the same link-dedup
question part 1 asked of everything else: dedupes on `(user_id, university_id, source,
last_changed_at)` via `university_notification_log` (migration `0078`), not link — clean, same
established pattern as `deadline_notification_log`. `features/notifications/categories.ts` was
written to exclude it, then updated once the merge surfaced that it shouldn't be anymore — left
a comment there naming the commit, so the next person doesn't have to re-derive why the list
looks the way it does.

**The popover** (`features/app-shell/notification-bell.tsx`): unchanged except one addition — a
"View all" footer link to `/notifications`, always shown (even when everything visible is
read, since there can be older history past the 20 shown). This is the "honest preview" half of
oryn-a7's own framing: the popover no longer has to pretend it's the whole story.

**Deliberately not done**: no grouping — flat reverse-chronological, matching oryn-a7's explicit
instruction not to add it just because a page makes it possible. No unread-only filter — not
asked for, category filter plus per-row read state covers what was scoped.

`main` at `1557180d` confirmed clean immediately before pushing.
